# Bend 2 の速さを C と GPU で比べる

Bend 2 のガイドは「C 並みの速さと CUDA 並みの並列性」をうたい、「mandelbrot のような一様な数値計算は GPU が速く、n-queens のような
分岐の多い仕事は CPU が速い」と書く（`bend guide` の冒頭と「Parallelism」）。これを、同じ計算を C（OpenMP）でも書いて確かめた。
GPU を Windows で動かす方法と、その制限は [gpu.md](gpu.md) にある。

特に断りのない記述は、実際に動かして確かめたこと。ガイドなどの記述だけに基づくものには「（文書のみ）」、
確かめていないものには「（未確認）」と書いた。

## 分かったこと

- **一様な数値計算（mandelbrot）では、Bend は C とほぼ同じ速さで、スレッド数にも C と同じように伸びる。** 1 スレッドでは Bend のほうが 5% ほど速かった。
- **同じ mandelbrot を GPU に載せると、反復 4096 回で CPU 12 スレッドの約 8 倍速い。** ただし GPU には毎回約 1.7 秒の固定費があり、
  軽い仕事（反復 256 回、CPU で 1.3〜1.5 秒）では CPU に負ける。
- **分岐の多い仕事（n-queens）では、Bend は 1 スレッドで C の 3〜4 倍遅い。** 素直に書くと 12 スレッドでも 1.5 倍しか伸びないが、
  C と同じく仕事を均等に割ると 4〜6 倍に伸びた。GPU は割り方によらず CPU より遅く、ガイドの言うとおりの傾向だった。
- **ガイドが GPU の見せ場とするレイトレーサー（公式 demo）では、GPU は CPU 12 スレッドの約半分の速さだった。** 1 コマ（1024×1024 画素）が
  CPU 12 スレッドで 69〜101 ms、GPU で 150〜181 ms。CPU が絵を読み出さなくても変わらなかった。
- **証明付きの HTTP サーバーは、毎秒 1.7〜2.0 万件の要求をさばいた。** Go の最小のサーバーの 8 割前後で、Node.js の 2.5 倍以上だった。
- **CPU・GPU・C の答えは、すべての条件で一致した。** F32 の丸めも含めて一致させるため、C は `-ffp-contract=off` でビルドした（後述）。

## 計測の条件

- 機: Windows 10、AMD Ryzen 5 3600（6 コア 12 スレッド）、RTX 5060 Ti。wslc のコンテナ（`bend2-gpu` イメージ）の中で測った。環境の詳細は
  [environments.md](environments.md) の「確かめた環境」。
- 題材と計測のスクリプトは `bench/` にある。`bench/run.sh mandel|threads|nqueens` が、各条件を 2 回ずつ、条件を交互に並べて測る。
  時間はプロセスの起動から終了まで（GPU では CUDA の初期化と `.gpu` の読み込みを含む）。生の値は機ごとのフォルダ
  （この文書の値は `bench/results/ryzen5-3600-wslc/`）の TSV。
- Bend の CPU は `--gpu off`、GPU は `bench/build-wsl-gpu.sh` でパッチを当てたビルドを `--gpu 1GB --threads 1` で走らせた（[gpu.md](gpu.md)）。
  C は clang 19 の `-O3 -fopenmp`。
- 表の値は 2 回の計測の両方を載せた。

この文書の値は、`bench/run.sh` が wslc の GPU 用イメージの中でしか動かなかったころの版で測った。いまの `bench/run.sh` は、
bend が PATH にある環境（Linux、macOS、Containerfile のイメージの中）ならどこでも動き、スレッド数・C 版の OpenMP・GPU（CUDA、
WSL2 の回避、Metal）を環境から決める。測る条件と行の並びは以前の版と同じにしてあるが、Windows で新しい版を回してはいない。
Docker の Linux では、小さな大きさ（`BENCH_QUICK=1`）で全部の条件が動くことだけを確かめた。macOS（Apple M2）では本番の大きさで測った
（下の「macOS（Apple M2）」）。

同じ日の別の時間帯に同じ計測をしたところ、CPU の結果が全体に 1.3〜1.8 倍遅く出た（mandelbrot 反復 256 回・1 スレッドで Bend 14.9 秒、C 14.5 秒）。
同じ回の中の 2 回はよく揃っていたので、機の別の負荷を拾っていたと推定している（未確認）。比べるときは、同じ回の中の値どうしで比べる。

## mandelbrot: GPU は重い計算で 8 倍速い。軽い計算では固定費で負ける

4096×4096 画素の脱出時間を数えて合計する（`bench/mandel.bend`、`bench/mandel.c`）。途中で抜けずに毎回決まった回数まわすので、
どの画素も同じ手数になる。GPU のレーンが揃う、GPU 向きの形である。画像は 4 分木で 4^7 = 16384 枚のタイルに分け、
タイルの中は平らなループで回す（`bend guide shaders` の勧める形）。

| 反復の回数 | Bend CPU 12 スレッド | Bend GPU | C 12 スレッド |
|---|---|---|---|
| 0 | 11・11 ms | 1,752・1,594 ms | 7・5 ms |
| 256 | 1,494・1,334 ms | 2,091・1,820 ms | 1,265・1,482 ms |
| 1,024 | 5,311・5,201 ms | 2,078・1,883 ms | 5,647・4,776 ms |
| 4,096 | 19,715・19,906 ms | 2,532・2,536 ms | 19,591・21,410 ms |
| 16,384 | （測らず） | 4,892・5,088 ms | （測らず） |

反復 0 回の GPU の約 1.7 秒が固定費で、CUDA の初期化と `.gpu` の読み込みにかかっている。反復 4,096 回から 16,384 回に増やしたときの
差（約 2.5 秒で 12,288 回ぶん）から見ると、計算そのものは CPU 12 スレッドの 20 倍余り速いと推定する（反復 1 回あたり GPU 約 0.2 ms、CPU 12 スレッド約 4.8 ms。どちらも 2 点の差からの割り算で、内訳は測っていない）。

### スレッド数ごとの伸びは、Bend と C でほぼ同じ

反復 256 回で、スレッド数を変えた（`bench/run.sh threads`）。

| スレッド数 | Bend | C |
|---|---|---|
| 1 | 10,361・10,336 ms | 10,878・10,914 ms |
| 2 | 5,274・5,315 ms | 5,570・5,652 ms |
| 4 | 2,741・2,876 ms | 2,861・3,184 ms |
| 6 | 2,067・2,432 ms | 1,951・2,033 ms |
| 12 | 1,256・1,207 ms | 1,403・1,145 ms |

6 コアまではほぼ比例して伸び、12 スレッド（SMT）で 1 スレッドの約 8.5 倍になった。この題材に関しては「C 並みの速さ」が成り立っている。

## n-queens: 割り方を揃えると Bend も 12 スレッドで 6 倍伸びる。それでも C の 4〜5 倍遅く、GPU は CPU より遅い

N クイーンの解の数を、列と 2 本の斜めの利きをビットで持つ、よくある形で数える。書き方を 2 通り用意した。

- **素直な版**（`bench/nqueens.bend`）: 候補の列ごとに「置いた場合」と「次の列を試す場合」を parallel let で並列に分ける。
- **均等な版**（`bench/nqueens_split.bend`）: 最初の 2 行の置き方（N×N 通り）を 256 枚の葉に割り当て、深さ 8 の均等な二分木で並列に配る。
  葉の中は並列にせず、逐次に数える。C 版（`bench/nqueens.c`）と同じ割り方で、C 版は同じ N×N 通りを OpenMP で並列にする。

計測は 2 回に分けて行い、各回で 2 回ずつ測った。この計測の間は機に別の負荷が掛かっていたとみられ、同じ条件でもばらつきが大きかったので、
4 回の最小〜最大を載せる（生の値は `bench/results/ryzen5-3600-wslc/nqueens.tsv`）。

| N | 条件 | 1 スレッド | 12 スレッド | GPU |
|---|---|---|---|---|
| 13 | Bend 素直な版 | 130〜160 ms | 85〜112 ms | 2,234〜3,062 ms |
| 13 | Bend 均等な版 | 133〜172 ms | 30〜46 ms | 1,920〜2,597 ms |
| 13 | C | 39〜59 ms | 9〜60 ms | — |
| 14 | Bend 素直な版 | 731〜991 ms | 537〜1,021 ms | 5,099〜6,888 ms |
| 14 | Bend 均等な版 | 775〜1,014 ms | 142〜191 ms | 3,283〜4,575 ms |
| 14 | C | 205〜273 ms | 32〜66 ms | — |
| 15 | Bend 素直な版 | 4,743〜6,211 ms | 3,116〜4,763 ms | 23,048〜28,074 ms |
| 15 | Bend 均等な版 | 4,764〜6,237 ms | 755〜1,391 ms | 10,888〜13,216 ms |
| 15 | C | 1,278〜1,718 ms | 172〜610 ms | — |

N=16 は別の回に 1 回だけ、素直な版と C で測った: Bend 1 スレッド 42,596 ms、12 スレッド 31,276 ms、GPU 225,841 ms、C 1 スレッド 12,426 ms、12 スレッド 2,245 ms。

### 素直な版が伸びないのは、枝の重さが揃わないため

素直な版は、12 スレッドにしても 1 スレッドの 1.3〜1.5 倍にしかならない。均等な版は 1 スレッドの速さがほぼ同じまま、12 スレッドで 4〜6 倍に伸びた
（N=15 の値の良いほうどうしで 4,764 → 755 ms）。1 スレッドでの差が無いので、違いは割り方だけから来ている。

ガイドによれば、Bend のスケジューラは仕事を一度コアに渡したら動かさない。parallel let の 2 つの呼び出しの重さを揃えるのは書き手の責任である
（文書のみ）。素直な版では「置いた場合」の枝がずっと重いので、重い枝を受け取ったコアだけが働き続ける。並列にするなら、
重さの揃った仕事を均等な木で配る。

均等に割っても、1 スレッドでは C の 3〜4 倍遅い。12 スレッドの比は、ばらつきのせいで 2〜8 倍と幅がある。

### GPU は、均等に割っても CPU より遅い

均等な版は GPU でも素直な版の約半分の時間になったが、CPU 12 スレッドの 8〜18 倍かかる。葉が 256 枚しか無く、
GPU の 16,384 レーンのほとんどが遊ぶうえ、各レーンが別々の深さの探索をする。ガイドの言う「divergent work」そのものである。
`bend guide shaders` は、GPU のレーンは直列の仕事で CPU の P コアの約 1/75 の速さだと書いている（文書のみ）。

## macOS（Apple M2）: CPU では Bend と C の差が Ryzen と同じ形で出る。GPU は macOS に打ち切られることがある

Apple M2（高性能コア 4・高効率コア 4、16 GB）の macOS 26.6.2 で、いまの `bench/run.sh` を回した（2026-10-01）。C は Apple clang 21 に
Homebrew の libomp。GPU は、2.0.34 では Metal のコンパイラが落ちるので（[gpu.md](gpu.md) の「macOS」）、2.0.27 を `BEND_GPU_HOME` で指して使った。
生の値は `bench/results/m2-macos/`。

Mac を使っている最中に測ったので、条件を次のように揃えた。題材の前ごとに、`top` で測った CPU の空きが 80% 以上の状態が 30 秒続くのを待ち、
Docker Desktop は止めた。それでも画面の描画（`WindowServer`）や Claude のアプリが合わせて CPU の 2 割ほどを使っていた。最初は空き 90% を
条件にしたが、15 分待って 90% に届いたのは 1 回だけだった。Ryzen の値とは機も条件も違うので、比べるのは同じ表の中の値どうしにする。

### CPU: mandelbrot は C と同じ速さ、n-queens は C の 3〜4 倍遅い

| 題材 | Bend 1 スレッド | Bend 8 スレッド | C 1 スレッド | C 8 スレッド |
|---|---|---|---|---|
| mandelbrot 反復 256 回 | 12,325・12,288 ms | 2,146・2,139 ms | 13,238・12,511 ms | 2,175・2,216 ms |
| mandelbrot 反復 4,096 回 | （測らず） | 35,422・35,618 ms | （測らず） | 36,697・39,550 ms |
| n-queens 15（素直な版） | 3,451・3,347 ms | 2,304・2,243 ms | 937・945 ms | 169・165 ms |
| n-queens 15（均等な版） | 3,180・3,148 ms | 661・640 ms | （同上） | （同上） |

mandelbrot の 1 スレッドの値はスレッド数の計測（`run.sh threads`）、それ以外は `run.sh mandel`・`run.sh nqueens` を GPU なし
（`BEND_GPU=off`）で回した値。答えはすべての条件で一致した。Ryzen と同じく、n-queens の素直な版は 8 スレッドでも 1.5 倍しか伸びず、
均等な版は 5 倍に伸びた。

### 高効率コアに仕事が回り始めると、Bend がわずかに遅れる

mandelbrot 反復 256 回で、スレッド数を 1 から 8 まで 1 ずつ変えた。1 スレッドの速い方の値に対する倍率で示す。

| スレッド数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Bend | 1.00 | 1.91 | 2.70 | 3.66 | 4.03 | 4.53 | 5.23 | 5.80 |
| C | 1.00 | 1.91 | 2.75 | 3.66 | 4.28 | 4.90 | 5.36 | 5.84 |

高性能コアの数（4）までは、Bend と C の倍率が揃った。5・6 スレッドでは Bend が C より 6〜8% 遅れ、8 スレッドでまた揃った。
Bend のスケジューラは仕事を最初に配ったコアから動かさない（`bend guide` の「Parallelism」の「every task is handed to a core exactly once」）。
一方、C は OpenMP の `schedule(dynamic, 16)` で、空いたスレッドが次の行を取る。そのため、遅い高効率コアに配られた仕事を
Bend だけが待つと推定している。8 スレッドで揃う理由は分からない。どのスレッドがどのコアで走ったかは測っていない。

### GPU（Metal、2.0.27）: 固定費は CUDA より小さい。長い仕事は macOS に打ち切られた

| 題材 | Bend 8 スレッド | Bend GPU |
|---|---|---|
| mandelbrot 反復 0 回 | 8 ms | 449 ms |
| mandelbrot 反復 256 回 | 2,211 ms | 490 ms |
| mandelbrot 反復 1,024 回 | 8,745 ms | 1,231 ms |
| n-queens 14（素直な版・均等な版） | 330・335 ms／127・100 ms | 12,467・13,718 ms／6,332・6,688 ms |
| n-queens 15（素直な版・均等な版） | 2,215・2,220 ms／628 ms | 82,784 ms／36,421 ms |

GPU の固定費（反復 0 回）は約 0.45 秒で、CUDA の約 1.7 秒より小さい。反復 1,024 回で CPU 8 スレッドの約 7 倍速い。n-queens は
Ryzen と同じく、GPU が CPU より 1 桁以上遅い。答えはどれも CPU と一致した。

mandelbrot の反復 4,096 回と、n-queens 15 の 2 回目の GPU は、`bend: Impacting Interactivity
(0000000e:kIOGPUCommandBufferCallbackErrorImpactingInteractivity)` で止まった。GPU の 1 回の仕事が長く、画面の描画と取り合った
ために macOS が打ち切ったと推定している。午前に手で回したときは、反復 4,096 回が 4.4〜4.9 秒で通っていた（[gpu.md](gpu.md)）。
打ち切られた回の値は、その手前までを `bench/results/m2-macos/*-gpu.tsv` に残した。

## レイトレーサー: GPU は CPU 12 スレッドの約半分の速さ

ガイドが GPU の一番の見せ場として挙げる描画の仕事を、公式の demo `app_ray_tracer_3d` で測った。球の並ぶ床と空を ray marching で描き、
1 コマ 1024×1024 画素を、ファイル中ただ 1 か所の bang（`Fly.scene!`）で作る。`App.run` は窓を開くので、画面を出さずにコマを回す
計測用のプログラム（`bench/raytrace/frames.bend`）を書いた。公式のコードはリポジトリに写さず、`bench/raytrace/fetch.sh` で commit を固定して取ってくる。

右矢印キーを押したままにした状態から始め、コマごとにカメラを回しながら描く。k=1 と k=11 の時間の差を 10 で割って、起動の固定費を除いた
1 コマの時間とした（`bench/raytrace/run.sh`、各 2 回。生の値は `bench/results/ryzen5-3600-wslc/raytrace.tsv`）。読み出しは 2 通りで測った。
「合計」は毎コマ CPU で全画素の色を足す（CPU と GPU で同じ絵になったかの照合を兼ねる）。「捨てる」は合計せずに GPU の上で捨てる
（`Image.drop!`。公式の `App.turn` と同じ）。

| 条件 | 1 コマ（合計） | 1 コマ（捨てる） | FPS 換算 |
|---|---|---|---|
| CPU 1 スレッド | 531〜549 ms | 528〜543 ms | 約 1.9 |
| CPU 12 スレッド | 69〜74 ms | 79〜101 ms | 約 10〜14 |
| GPU（RTX 5060 Ti、WSL の回避） | 150〜170 ms | 167〜181 ms | 約 6 |

全画素の合計は、CPU と GPU で一致した（11 コマで 118964864）。GPU が遅いのは、CPU が絵を読み出すためではない（捨てても変わらない）。
`bend guide shaders` は、CUDA ではホストが作ったデータを GPU が読むたびにページが PCIe を行き来し、RTX 4090 でも 17〜19 FPS にとどまると書いている
（文書のみ）。この demo はシーンを関数で持ち、データの行き来は少ないはずなので、WSL2 の managed memory の重さが重なっていると推定している（未確認）。
macOS の Metal では測っていない。

## サーバー: 証明付きの Bend は、Go の 8 割前後をさばく

固定の短い文（`fast` と改行）を返すだけの最小のサーバーを、Bend・Node.js・Go で用意し、負荷ツール `hey`（Go 製、v0.1.4）で 2 万件の要求を
同時 50 本で送った（`bench/server/run.sh`、各 2 回。生の値は `bench/results/ryzen5-3600-wslc/server.tsv`）。

- Bend は `concurrency/stall.bend` の `/`（証明の検査を通るサーバー。要求ごとに `IO.spawn` で処理する）。ネイティブビルド。
- Node.js 22（`bench/server/node.js`）と Go 1.23（`bench/server/main.go`）は、標準ライブラリの HTTP サーバー。
- Bend のサーバーは応答のたびに接続を閉じるので、どれも `-disable-keepalive` で、要求ごとに接続を張り直す条件に揃えた。
- サーバーと `hey` は同じコンテナの中で動かし、12 スレッドを分け合う。Node.js は 1 本のスレッドで動き、Bend と Go は全コアを使う。

| サーバー | 毎秒の要求数 | 遅延の中央値 | 遅延の 99% 点 |
|---|---|---|---|
| Bend | 16,739・20,119 | 2.5・2.4 ms | 10.4・5.1 ms |
| Go | 23,508・21,216 | 1.6・1.8 ms | 6.6・7.2 ms |
| Node.js | 7,182・6,758 | 6.4・6.6 ms | 13.9・15.7 ms |

どれも 2 万件すべてに 200 を返した。Bend が Node.js より速いのは、全コアを使えることが大きいと考える。接続を張り直さない条件
（keep-alive）では、Bend のサーバーが接続を閉じる作りなので比べていない。

## 答えの一致と、FMA の罠

mandelbrot の C 版を、最初は既定の `-O3` でビルドするつもりだった。clang は既定で、1 つの式の中の掛け算と足し算を FMA 命令にまとめうる
（`-ffp-contract=on`）。FMA にすると丸めが 1 回減り、F32 の結果が Bend 版とずれうる。`-ffp-contract=off` を付けると、Bend の CPU・GPU と
C の合計が、C でも測った反復 0〜4,096 回のすべてで一致した（16,384 回は GPU だけで測った）。bend の GPU ビルドも NVRTC に `--fmad=false` を渡している（生成された C の `gpu_make`）。

JS に出した Bend も同じ値を返した。ブラウザの中で先頭 64 行ぶんの合計を出すと、C と同じ 467,323 だった（[web.md](web.md)）。
