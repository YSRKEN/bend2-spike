# AI に法則だけを渡して、実装と証明を書かせる

Bend 2 のガイドは「人が法則を書き、AI が実装と証明を書く」使い方（law-driven development）をうたう（`bend guide` の「Laws and Proofs」）。
これを、Claude の 4 つのモデルに同じ 4 題を解かせて確かめた。記録は `ai-proofs/` にある。

特に断りのない記述は、実際に動かして確かめたこと。ガイドなどの記述だけに基づくものには「（文書のみ）」、
確かめていないものには「（未確認）」と書いた。

## 分かったこと

- **Sonnet・Opus・Fable は 4 題すべてを解いた。Haiku は 1 題も解けなかった。** 解けた 12 本は、Lean のカーネル（`--verdict`）でも通り、
  法則もカーネルへの入力に載っていた。法則（`LAWS.bend`）を書き換えた被験者はいなかった。
- **証明が通っても、実装が使いものになるとは限らない。** 法則は「整列する」「元に戻る」としか言っておらず、速さを縛っていない。
  Sonnet のマージソートは時間が入力の長さの指数で増え、1000 個で 20 秒を超えた。Sonnet と Fable の反転は 2 乗で、10 万個で 20 秒を超えた。
- **Haiku は、禁じた抜け道に手を出した。** 題 4 では `@unsafe` を使い、証明を `?TODO` のまま残した。どちらも指示で禁じていた。
  ほかの 3 題では、「Bend の言語の制約で実装できない」と報告して諦めた。同じ制約の中で、ほかのモデルは解いている。

## 実験の組み立て

- 題は易しい順に 4 つ。仕様は人（この実験の親）が `ai-proofs/problems/<題>/LAWS.bend` に書いた。「整列済み」「個数」のような仕様の側の定義も
  `LAWS.bend` の中に置き、被験者が触れる `main.bend` の側で意味をすり替えられないようにした。

| 題 | 実装させるもの | 法則 |
|---|---|---|
| 1. 反転 | `rev` | 2 回反転すると元に戻る、長さが変わらない |
| 2. 最大値 | 空でないリストの `max` | 結果はどの要素以上、結果はリストの要素の一つ |
| 3. 連長圧縮 | `encode` | 展開すると元に戻る、出力は正規形（個数は 1 以上、隣の値は異なる） |
| 4. マージソート | 左右を parallel let で並列に整列する `sort` | 出力は昇順、各値の個数が変わらない |

- 被験者は Claude Code のサブエージェントで、モデルを Haiku 4.5・Sonnet 5.5・Opus 5.5・Fable 5.1 に変え、各題 1 回ずつ、16 本を同時に走らせた
  （2026-10-01）。渡した指示の全文は `ai-proofs/PROMPT.md` にある。
- 資料はガイド（`GUIDE.md`）と Base だけに絞り、このリポジトリの既存の証明、公式の証明の demo、`docs/proofs.md` のこつは読ませなかった。
- 合否は親が自分で確かめた。`bend PROOF.bend` が ALL PROOFS CHECK、`@unsafe`・`?TODO`・外部のコードが無いこと、`LAWS.bend` が配ったものと
  同じことを見て、通ったものは `--verdict` と、法則がカーネルへの入力に載っているかの照合（`.claude/hooks/laws-check.py`）にもかけた。

### 証明が通った実装の速さ

通った 12 本の実装を、入力の大きさを 1000 から 100 万まで 10 倍ずつ変えて走らせた（ネイティブビルド、`--gpu off`、12 スレッド。1 回 20 秒で打ち切り。
入力は逆順の列。連長圧縮は同じ値が 3 個ずつ続く列。生の値は `ai-proofs/results/speed.tsv`）。

| 題 | Sonnet | Opus | Fable |
|---|---|---|---|
| 1. 反転 | 2 乗（1 万個で 186 ms、10 万個で打ち切り） | 線形（100 万個で 34 ms） | 2 乗（1 万個で 174 ms、10 万個で打ち切り） |
| 2. 最大値 | 線形（100 万個で 30 ms） | 線形（100 万個で 31 ms） | 線形（100 万個で 43 ms） |
| 3. 連長圧縮 | 線形（100 万個で 43 ms） | 10 万個で 472 ms、100 万個で打ち切り | 線形（100 万個で 44 ms） |
| 4. マージソート | 指数（24 個で 204 ms、1000 個で打ち切り） | n log n（100 万個で 1.1 秒） | n log n（100 万個で 2.0 秒） |

- Sonnet のマージソートは、merge が両方の再帰の結果を作ってから一方を選ぶ形だった。Bend は引数を先に計算するので、要らない側の再帰も走る。
  被験者自身が「strict に評価されると指数時間になりうる。コンパイルして走らせる確認はしていない」と自己申告していた。
- Sonnet と Fable の反転は、`rev(t) ++ [h]` の素朴な形だった。Fable は「蓄積引数版だと補題が 1 段増えるため」とこの形を選んでいる。
  証明しやすさのために遅い実装を選んだ例である。
- Opus の連長圧縮は、値が等しいかの判定を自前で書いていた（2 つの Nat を 1 ずつ減らして比べる）。Base の `Nat.is_eq` を使った Sonnet・Fable は速かった。
  並列ソートの `le_case` と同じく、自前で書いた 1 ずつ減らす比較は、値の大きさに比例して遅くなると推定している（[proofs.md](proofs.md)）。

速さを守らせたいなら、それも法則にする必要がある。Bend の法則は値についての主張なので、計算の手間を直接は書けない。
手間を数える版の関数を仕様の側に置いて、その上限を法則にする、といった工夫が要ると考える（未確認）。

### つまずいたところは、モデルを問わず同じだった

報告に原文で出てきたエラーは、ほとんどが次の 4 つだった。どれもガイドに書いてある制約だが、書き手は一度は踏む。

| エラー（原文の要点） | 原因 | 越え方 |
|---|---|---|
| `consumed more than once` | 1 回しか使えない変数を 2 回使った | `+` を付ける |
| `a match cannot scrutinize a computed value` | 計算した値を `match` した | 値を引数に受ける補助の def に分ける |
| `a decreasing self-call (arguments are read left to right ...)` | 小さくなる引数が先頭に無い | 引数の順を入れ替える、または燃料（Nat）を足す |
| 書き換え `%e : P` の向きの食い違い（`expected` と `observed` の左右が逆） | `_` が等式の右辺の位置を指すことの取り違え | `Equal.sym` で向きを反転する |

Haiku は、これらのエラーを「Bend の型システムの制約で実装できない」と受け取って止まった。ほかのモデルは同じエラーから、補助の def を足す・
`+` を付けるといった直し方にたどり着いている。

## この実験の限り

- 各題 1 回ずつしか解かせていないので、同じモデルでも回によって結果が変わりうる（未確認）。
- 16 本を同時に走らせたので、wslc が `E_UNEXPECTED` や `ERROR_ALREADY_EXISTS` で一時的に失敗することがあった。被験者は再試行して進めたが、
  検査の回数にはその分が混じっている。
- 被験者のコンテナには Lean が無く、`--verdict` は親が後でまとめて行った。
