# 法則と証明の書き方

Bend 2 では、仕様を「法則（law）」として書き、それが成り立つことを証明し、コンパイラに機械的に検査させられる。
この文書は、`server/` の HTTP サーバーで法則を書いて証明したときに分かったことをまとめたもの。
何を証明したか（と、しなかったか）を知りたいだけなら、最後の「このサーバーで証明したこと、しなかったこと」から読めばよい。

特に断りのない記述は、実際に動かして確かめたこと。ガイドなどの記述だけに基づくものには「（文書のみ）」、
確かめていないものには「（未確認）」と書いた。

## ファイルは 3 つに分ける: 実装、法則、証明

公式の慣習に従い、`server/` に次の 3 つを置いた。

| ファイル | 役割 | 書く人（ガイドの想定） |
|---|---|---|
| `server.bend` | 実装 | AI |
| `LAWS.bend` | 法則（仕様）。`server.bend` を import し、`law 名前:` で主張を書く | 人間 |
| `PROOF.bend` | 証明。`LAWS.bend` を import し、`def Laws.名前` で各法則を証明する | AI |

`LAWS.bend` だけを検査すると、証明の無い法則が「TODOs found」として残り、必ず失敗する。検査は `PROOF.bend` に対して行う。
同じ理由で、`LAWS.bend` だけを import したプログラムは実行できない。`LAWS.bend` と `PROOF.bend` の両方を import すれば、
仕様の側に書いた関数も実行できる。

## 証明を書くときのこつ

### 計算で両辺が一致するなら `{==}` で済む。止まったら、その変数で場合分けする

変数が残って計算が進まないとき（例: `String.starts_with(name, "")`）は、その変数で `match` して場合分けすれば、
各場合が `{==}` で通る。`hello_echo` はこの形で証明した。

### 基本的な補題は自分で用意する

Base にある補題は `Equal.cong`・`Equal.sym`・`Equal.trans` などにほぼ限られる。`Nat.add` の結合法則、
`add_zero`、`s ++ "" == s` は自作した。

### 書き換え `%e : P` は、ゴールの中の右辺を左辺に変える

`e : {a == b}` のとき、`P` にはゴールの `b` の位置を `_` にしたものを書く。書き換えた後のゴールでは、そこが `a` になる。
向きが逆なら、法則の左右を入れ替えて書く（`split_prefix` はそうした）か、`Equal.sym` を使う。

補題をつなぐだけなら、書き換えより `Equal.trans` と `Equal.cong` をそのまま使うほうが読みやすい（`hello_request`）。

### 累積引数のある再帰は、累積引数を一般化した補題を帰納法で示す

`utf8.bytes(s, acc)` のような関数は、`acc + f(s) == g(s, acc)` の形の補題を立てて帰納法で示す。
停止性の検査は引数を左から見るので、小さくなっていく引数を先頭に置く。

### 「空白を含まない」のような前提は、1 要素ずつの証拠を並べた型で書く

`Spec.NoSpace` は、1 文字ごとに `{False{} == Char.is_eq(c, ' ')}` を並べた型にした。証明の側ではこの組を分解し、
書き換えに使う。等式の向きは、書き換えで使う向きに合わせて定義しておく。

### 失敗時のメッセージは長いので、先頭だけ見る

期待値と実際の値は、文字列を 1 文字ずつ展開した形で出る。`bend PROOF.bend --check-only 2>&1 | cut -c1-200` のように
先頭だけ見るとよい。

## 証明が通っただけでは足りない。毎回ここまで確かめる

証明が通っても、法則が十分だとは限らない。このリポジトリでは、証明を足したり変えたりするたびに次を行う。

1. **両方の検査を通す。** `bend PROOF.bend --check-only` と `bend PROOF.bend --verdict` の両方が `ALL PROOFS CHECK` になること。
   `--verdict` は Lean で証明済みのカーネルによる再検査で、Lean v4.34.0 が要る（[environments.md](environments.md)）。
2. **わざと壊して、証明が落ちることを確かめる。** 実装か法則を 1 か所だけ壊し、証明が失敗することを見る。
   壊した箇所が実際に変わったこと（grep で確かめる）と、失敗の理由が狙いどおりであることも確かめる。
   置換が当たっていなかったり、別の理由で失敗していたりしたことがあった。
3. **前提が満たせることを確かめる。** 前提付きの法則は、具体例に当てはめて前提の証拠を実際に作る
   （`main` の型に具体的な等式を書いて通す）。作れないなら、法則が空虚に成り立っているおそれがある。
4. **仕様そのものを外部と照合する。** 法則の側に書いた仕様（`Spec.encode`）は、Python など別の実装と出力を比べる。
   `"Aé日😀"` で一致を確かめた。
5. **証明の範囲外を書き出す。** 入出力、受信の分割、ランタイム、変換処理などは証明が届かない
   （ガイドにも変換処理について「the translation has no proof」とある）。

2 の「壊して確かめる」で、実際に穴が見つかった。`utf8.bytes` が正しいことは証明できていたのに、`respond` が
`utf8.bytes` の代わりに `String.length` を使うよう戻しても、証明は通ってしまった。「部品が正しい」という法則だけでは、
「その部品を使っている」ことは保証されない。応答全体の形式を定める法則（`response_format`）を足して塞いだ。

## `--verdict` は型検査の二重目の網。カーネルは誤りを捕まえるが、網にも穴がある

`--verdict` は、bend2（TypeScript で書かれた型検査）が通した def を、Lean で証明された小さなカーネル（BendTT）でもう一度検査する。
`ALL PROOFS CHECK` になるのは、両方が受け入れ、`@unsafe` や外部のコードに頼っていないときだけ（`bend guide` の 328〜332 行）。
カーネルだけが捕まえる誤りは、bend2 が誤って通したものに限られる。macOS（bend 2.0.34、Lean 4.34.0）で 2026-10-01 に次を確かめた。

### カーネルは、bend2 を通さずに渡した偽の証明を拒む

`bend x.bend -o x.bendtt` でカーネルへの入力を書き出し、手で書き換えて、カーネル（`~/.bend/bendtt/<ハッシュ>/bendtt`）に直接渡した。

| 渡したもの | カーネルの判定 |
|---|---|
| `1 + 1 == 2` を `{==}` で証明（対照） | `ALL PROOFS CHECK`（終了コード 0） |
| 主張だけを `1 + 1 == 3` に書き換えた | `SOME PROOFS FAIL`、期待値と実際の値を示す（終了コード 1） |
| `1 + 1 == 3` を自分自身を呼ぶ def で「証明」 | `SOME PROOFS FAIL`、`calls that descend`（停止しない） |
| 同じ主張を、互いを呼び合う 2 つの def で「証明」 | `SOME PROOFS FAIL`、`calls that descend` |
| `Nat.add` の定義を「0 + y = y + 1」にすり替え、`1 + 1 == 3` を `{==}` で証明 | `ALL PROOFS CHECK` |

最後の行のとおり、カーネルが保証するのは「渡された定義のもとで証明が正しい」ことまでで、定義や法則が意図どおりに訳されたかは保証しない。
ガイドの「the translation has no proof, so read it to confirm a law」はこのことを言っている。

### bend2 は通すがカーネルは拒む例が、2.0.34 にもある

[bendlang/bend#1167](https://github.com/bendlang/bend/issues/1167)（未解決）の例は、2.0.34 でも `--check-only` が通り、`--verdict` が
「TypeScript の実装と形式化されたカーネルの食い違い」という知らせ付きで `SOME PROOFS FAIL` になった。構成子を組み直して自分を呼ぶ再帰
（`height(Node{rest})`）で、issue のコメントでは、bend2 が通す形は実際には必ず小さくなるので、偽を通したのではなくカーネルの規則が
狭いだけと分析されている。

偽を通した過去の例として、[bendlang/bend#902](https://github.com/bendlang/bend/issues/902)（2026-09-20 に修正済み）は、
`~` 引数を経由した 2 つの def の循環で `False{} == True{}` を `--check-only` に通していた。2.0.34 では bend2 の段階で
`a decreasing self-call` で止まり、カーネルまで届かない。issue の一覧で「verdict」を含むものは 46 件あり、うち 40 件が 2026-09-20 以降に立ち、21 件が未解決だった
（2026-10-01 に `gh search issues --repo bendlang/bend verdict` で数えた）。

### `--verdict` が、カーネルに見せないまま通してしまう def がある

[bendlang/bend#1186](https://github.com/bendlang/bend/issues/1186)（未解決）の穴も 2.0.34 で再現した。構成子の無い型の `~` 引数を
持つ def は、カーネルへの入力に載らず、範囲外とも報告されない。上の #1167 と同じ再帰をこの def の中に書くと、`--verdict` が
`ALL PROOFS CHECK` を出した。`~v: Void` を外しただけの同じ本体は、カーネルに渡って拒まれる。

```python
type Void is Data:

def skipped(~v: Void, t: Tree) -> Nat:   # Tree・Forest は #1167 と同じ
  match t:
    case Leaf{}: 0n
    case Node{End{}}: 1n
    case Node{Cons{+x, rest}}: Nat.max(1n+skipped(~v, x), skipped(~v, Node{rest}))
```

空の型の値は作れないので、この def は呼べず、ここから偽を導く方法は issue でも見つかっていない。法則の証明から呼ぶこともできなかった。
法則の `for` には `~` 引数を書けず（`expected : a name`）、証明の def から `helper(~v, n)` と呼ぶと、`~` には閉じた値しか渡せない
（`a template applied to closed ~ arguments`）と bend2 が止める。ただ「`--verdict` が通った def は
カーネルも検査した」とは言えなくなる。このリポジトリの証明は、`-o PROOF.bendtt` で書き出した入力に、法則 8 個（server 6 個、sort 2 個）が
すべて証明の本体付きで載っていて、`~` 引数を持つ def も無いので、この穴には当たっていない。

### 確かめ方に足すこと

上の「毎回ここまで確かめる」に加えて、`bend PROOF.bend -o PROOF.bendtt` を書き出し、法則の主張が訳されたあとも意図どおりであることを読む。
カーネルは定義のすり替えも、載らなかった def も教えてくれない。法則がすべて `LAWS.<名前> :` の形で載っていることは、commit 前のフックが
`.claude/hooks/laws-check.py` で機械的に確かめる（[claude-code.md](claude-code.md)）。手で照合したときは、名前空間の取り違えなどで
3 回数え直した。

## このサーバーで証明したこと、しなかったこと

証明した法則は 6 つ。どれもサーバーの純粋な部分についての主張で、`bend PROOF.bend --verdict` も通っている（クラウド環境で確認）。

| 法則 | 内容 |
|---|---|
| `root_page` | `/` への応答は決まった挨拶 |
| `hello_echo` | `/hello/<name>` の応答は、name をそのまま埋め込んだ 200 |
| `utf8_bytes` | `utf8.bytes` は、仕様どおりに符号化したバイト列の長さに等しい |
| `response_format` | 応答の形式全体（Content-Length が本文のバイト数で、空行の後に本文が続く） |
| `path_of_request` | 空白を含まない method と path なら、`path_of` は path を取り出す |
| `hello_request` | `<method> /hello/<name> <rest>` を受けると、name 入りの 200 を返す（`path_of` と `route` をつないだ全体） |

証明の範囲外として残したもの:

- `handle` などの入出力の部分。法則が述べているのは `route(path_of(req))` という純粋な部分だけで、
  接続の処理が実際にこの組み合わせを呼んでいることは述べていない。
- リクエスト行が分割されて届く場合。`TCP.recv` は 1 回（4096 バイト）しか読まない。
- `/pow2` と 404 のルーティング。
- メソッドの区別。GET 以外にも同じ応答を返す。
- パスのパーセントエンコードの復元（[language.md](language.md)）。
- 起動の部分（`main` と、待ち受け先 `BEND_HOST` の読み取り）。

公式のデモ（`io_http_server`）が証明しているのも、純粋な関数 `http_response` だけ
（「空行の後に本文」「応答が同じなら元のページも同じ」）だった。

## 並列ソートで証明したこと

`sort/` は、parallel let で左右を並列に整列する並列マージソートと、その正しさの証明である。公式の demo のうち、並列の bitonic sort
（`pure_par_sort`）が証明しているのは「葉の総和が変わらない」ことだけで、整列と並べ替えを証明している `proof_insertion_sort` は
逐次の挿入ソートだった。`sort/` はその間を埋める。

| 法則 | 内容 |
|---|---|
| `sort_sorted` | `sort` の出力は昇順に並んでいる |
| `sort_perm` | どの値 x も、`sort` の出力の中に、入力の木の葉と同じ回数だけ現れる（並べ替えである） |

`bend PROOF.bend --check-only` と `--verdict` の両方が ALL PROOFS CHECK（`--verdict` は Windows の Lean 入りのイメージで確認）。
補題は 9 個で、PROOF.bend は 146 行になった。比較には `proof_insertion_sort` の `LE`・`le_case`（どちらが小さいかの証拠を返す比較）を
出典を書いて借りた。

実装を壊した写しで検査すると、壊した場所に応じた法則で落ちた。merge の代わりに単につなぐと `sort_sorted` で、葉を 2 回出すと
`sort_perm` で落ちた。

### 比較の結果で分けるときは、枝を関数で渡す

`match` は計算した値を受けない（`a match cannot scrutinize a computed value: give it its own def`）。そこで比較の証拠を引数に取る
`branch(c, u => …, u => …)` を作って分けた。枝を値で渡すと両方とも計算されるので、`u => …` の関数で渡す。
再帰呼び出しがこの関数の中にあっても、停止性の検査は通った。

### 組み直した引数も「変わらない引数」として扱われる

Base の `List.merge` は停止のために燃料を持つが、`sort/` の `merge` には要らなかった。`merge(x <> xt, yt)` のように、
`match` でばらした第 1 引数を組み直して渡しても、停止性の検査は「変わらない引数」として受け、第 2 引数が小さくなることで通った。

### 証拠の値も 1 回しか使えない

`Sorted.from` は Type を返すので、その証拠は affine で、2 本の帰納法の仮定の両方に渡すことはできない。部分の証拠は補題（`.fin`）に
渡し、分岐ごとに 1 回ずつ使う形にした。

### 速さ: 12 スレッドで約 2.8 倍。入力が倍になると約 4 倍かかる

ネイティブビルド（`--gpu off`）で、逆順の入力を整列した。時間は入力の生成と結果の検査を含む実時間。

| 入力の個数 | 1 スレッド | 12 スレッド |
|---|---|---|
| 2^15 | 1,751・1,914 ms | 670・728 ms |
| 2^16 | 7,235・7,183 ms | 2,520・2,567 ms |
| 2^17 | 30,067・30,056 ms | 10,795・10,660 ms |

並列に伸びにくいのは、最上段の merge が逐次に全体をなめるためと考える。入力が倍になるごとに約 4 倍かかるのは、
`le_case` が 2 つの Nat を 1 ずつ減らしながら比べるので、比較の手間が値の大きさに比例するためと推定している（どちらも測っていない）。
証明のしやすさのために選んだ比較が、速さの上では足を引っぱっている。
