# 法則と証明の書き方

Bend 2 では、仕様を「法則（law）」として書き、それが成り立つことを証明し、コンパイラに機械的に検査させられる。
この文書は、`server/` の HTTP サーバーで法則を書いて証明したときに分かったことをまとめたもの。
何を証明したか（と、しなかったか）を知りたいだけなら、最後の「このサーバーで証明したこと、しなかったこと」から読めばよい。

特に断りのない記述は、実際に動かして確かめたこと。ガイドなどの記述だけに基づくものには「（文書のみ）」、
確かめていないものには「（未確認）」と書いた。

## ファイルは 3 つに分ける: 実装、法則、証明

公式の慣習に従い、`server/` に次の 3 つを置いた。

| ファイル | 役割 | 書く人（ガイドの想定） |
|---|---|---|
| `server.bend` | 実装 | AI |
| `LAWS.bend` | 法則（仕様）。`server.bend` を import し、`law 名前:` で主張を書く | 人間 |
| `PROOF.bend` | 証明。`LAWS.bend` を import し、`def Laws.名前` で各法則を証明する | AI |

`LAWS.bend` だけを検査すると、証明の無い法則が「TODOs found」として残り、必ず失敗する。検査は `PROOF.bend` に対して行う。
同じ理由で、`LAWS.bend` だけを import したプログラムは実行できない。`LAWS.bend` と `PROOF.bend` の両方を import すれば、
仕様の側に書いた関数も実行できる。

## 証明を書くときのこつ

### 計算で両辺が一致するなら `{==}` で済む。止まったら、その変数で場合分けする

変数が残って計算が進まないとき（例: `String.starts_with(name, "")`）は、その変数で `match` して場合分けすれば、
各場合が `{==}` で通る。`hello_echo` はこの形で証明した。

### 基本的な補題は自分で用意する

Base にある補題は `Equal.cong`・`Equal.sym`・`Equal.trans` などにほぼ限られる。`Nat.add` の結合法則、
`add_zero`、`s ++ "" == s` は自作した。

### 書き換え `%e : P` は、ゴールの中の右辺を左辺に変える

`e : {a == b}` のとき、`P` にはゴールの `b` の位置を `_` にしたものを書く。書き換えた後のゴールでは、そこが `a` になる。
向きが逆なら、法則の左右を入れ替えて書く（`split_prefix` はそうした）か、`Equal.sym` を使う。

補題をつなぐだけなら、書き換えより `Equal.trans` と `Equal.cong` をそのまま使うほうが読みやすい（`hello_request`）。

### 累積引数のある再帰は、累積引数を一般化した補題を帰納法で示す

`utf8.bytes(s, acc)` のような関数は、`acc + f(s) == g(s, acc)` の形の補題を立てて帰納法で示す。
停止性の検査は引数を左から見るので、小さくなっていく引数を先頭に置く。

### 「空白を含まない」のような前提は、1 要素ずつの証拠を並べた型で書く

`Spec.NoSpace` は、1 文字ごとに `{False{} == Char.is_eq(c, ' ')}` を並べた型にした。証明の側ではこの組を分解し、
書き換えに使う。等式の向きは、書き換えで使う向きに合わせて定義しておく。

### 失敗時のメッセージは長いので、先頭だけ見る

期待値と実際の値は、文字列を 1 文字ずつ展開した形で出る。`bend PROOF.bend --check-only 2>&1 | cut -c1-200` のように
先頭だけ見るとよい。

## 証明が通っただけでは足りない。毎回ここまで確かめる

証明が通っても、法則が十分だとは限らない。このリポジトリでは、証明を足したり変えたりするたびに次を行う。

1. **両方の検査を通す。** `bend PROOF.bend --check-only` と `bend PROOF.bend --verdict` の両方が `ALL PROOFS CHECK` になること。
   `--verdict` は Lean で証明済みのカーネルによる再検査で、Lean v4.34.0 が要る（[environments.md](environments.md)）。
2. **わざと壊して、証明が落ちることを確かめる。** 実装か法則を 1 か所だけ壊し、証明が失敗することを見る。
   壊した箇所が実際に変わったこと（grep で確かめる）と、失敗の理由が狙いどおりであることも確かめる。
   置換が当たっていなかったり、別の理由で失敗していたりしたことがあった。
3. **前提が満たせることを確かめる。** 前提付きの法則は、具体例に当てはめて前提の証拠を実際に作る
   （`main` の型に具体的な等式を書いて通す）。作れないなら、法則が空虚に成り立っているおそれがある。
4. **仕様そのものを外部と照合する。** 法則の側に書いた仕様（`Spec.encode`）は、Python など別の実装と出力を比べる。
   `"Aé日😀"` で一致を確かめた。
5. **証明の範囲外を書き出す。** 入出力、受信の分割、ランタイム、変換処理などは証明が届かない
   （ガイドにも変換処理について「the translation has no proof」とある）。

2 の「壊して確かめる」で、実際に穴が見つかった。`utf8.bytes` が正しいことは証明できていたのに、`respond` が
`utf8.bytes` の代わりに `String.length` を使うよう戻しても、証明は通ってしまった。「部品が正しい」という法則だけでは、
「その部品を使っている」ことは保証されない。応答全体の形式を定める法則（`response_format`）を足して塞いだ。

## 実用の道具で証明したときのこつ

[mcp-app.md](mcp-app.md) の MCP サーバーで、UTF-8・JSON・mbox・符号化語の法則を証明したときに分かったこと。

### ビット演算で書くと、記号のビットで計算が止まる。ビットを直接組み立てれば計算だけで閉じる

`Bool.and`・`Bool.or` は第 1 引数で場合分けするので、`U32.or(x, y)` の両方に記号のビットがあると計算が止まる。
Base の U32 の補題も `U32.add_comm` くらいしか無い。そこで、ビットの並びを `WCon` で直接組み立てて符号化と復号を書くと、
11 個の記号のビットを含んだまま計算が最後まで進み、UTF-8 の 2 バイトの往復が `{==}` だけで通った（`--verdict` も通る）。

```
# 11 ビットの値（下位から c0..c10、上位 21 ビットは 0）
def v11(c0: Bool, c1: Bool, c2: Bool, c3: Bool, c4: Bool, c5: Bool, c6: Bool, c7: Bool, c8: Bool, c9: Bool, c10: Bool) -> U32:
  U32{WCon{c0, WCon{c1, WCon{c2, WCon{c3, WCon{c4, WCon{c5, WCon{c6, WCon{c7, WCon{c8, WCon{c9, WCon{c10, Word.zero(21n)}}}}}}}}}}}}

# 2 バイト目（続きのバイト）: 10xxxxxx
def enc_lo(x: U32) -> U32:
  match x:
    case U32{WCon{c0, WCon{c1, WCon{c2, WCon{c3, WCon{c4, WCon{c5, rest}}}}}}}:
      U32{WCon{c0, WCon{c1, WCon{c2, WCon{c3, WCon{c4, WCon{c5, WCon{False{}, WCon{True{}, Word.zero(24n)}}}}}}}}}
```

比較（`c < 128`）も、上位のビットを `match` で見る形にする。この形は人が読んで正しいか判断しにくいので、
同じ仕様を Python などで素直に書いた読める版を置き、全域で突き合わせた。

### 不変条件は、値を作る唯一の関数で検査し、作った値に証明を持たせる

「復号した文字は全部スカラー値」を言うため、文字を作る入り口を `chr` 1 つに絞り、スカラー値でなければ U+FFFD にして、
作った値に証明を持たせた（依存ペア `&c: U32 -> {is_scalar(c) == True{} : Bool}`）。法則の証明は、復号の中身を追わずに
この型から帰納法で出た。

### 分類の結果を引数で受け取る（`.by` の形）と、証明は分類の結果で場合分けするだけで済む

`step(c) = step.by(classify(c), c, ...)` と書けば、証明は `classify(c)` の結果で場合分けし、前提 `{classify(c) == k}` で書き換えるだけで、
文字のビットに立ち入らない。生成側と解析側が同じ `classify(c)` を使うなら、両方を書き換える。

### 1 バイトずつの状態機械にすると、「区切って渡しても同じ」が帰納法の 3 行で出る

`feed(xs, st)` を左からの畳み込みにすれば、`feed(a ++ b, st) == feed(b, feed(a, st))` は `a` の帰納法で通る。
停止性もリストの末尾で再帰するだけで通る。入力を区切って読むサーバーの行の分割と mbox の区切りは、どちらもこの形にした。

### 連結した入力は、前半と後半に分けてから考える

「`gen(j) ++ R` を読むと…」と残りの入力 `R` を持ち回すと、連結の組み替えが証明のあちこちに要る。
`run(a ++ r, st) == run(r, run(a, st))` を 1 つ用意し、各補題を「`gen(j)` だけを読み終えた状態」の等式にすると、連結を分ける所でこれを使うだけで済んだ。

### 64 通りのような場合分けの木は生成し、生成したものと一致するかを試験で確かめる

Base64 の 1 文字（6 ビット、64 通り）や UTF-8 の 1 文字の往復は、ビットを全部分けて各葉を `{==}` で閉じた。木は Python で生成し、
証明のファイルの中身が生成したものと同じかを試験で確かめる。手で直すと説明と食い違うため。

### 複数の値を並べた `match` は、1 つずつ分ける鎖として計算が進む

`match c20 c19 c18 c17 c16:` を `case False{} False{} False{} False{} False{}:` と `case _ _ _ _ _:` に分けた関数について、
補題は `c20` から 1 ビットずつ分け、立っていればすぐ `{==}` で閉じる 15 葉の鎖で通った。5 ビットの組を全部（32 通り）分けなくてよかったので、
並べた値を左から 1 つずつ分ける形に展開していると推定する。

### `match` で場合分けすると、その変数に依存する前提の型も絞り込まれる

`h : {Bool.and(Bool.not(b), rest) == True{} : Bool}` を持ったまま `match b:` すると、`case True{}:` の枝では `h` の型が
`{False{} == True{} : Bool}` に計算され、矛盾として使えた。前提を別の def に渡し直さなくてよい。

### 帰納法の仮定は、関数として補助の def に渡せる

場合分けの順の決まりで補助の def に分けると、補助の def からは元の def を呼べない（相互再帰の禁止）。
帰納法の仮定を `o => rt(t, o, ...)` という関数にして渡すと、停止性の検査も通った。補助の def の側では、仮定の型を `@o: List<...> -> {...}` と書く。

### 書き換え `%e : P` は続けて何行でも書ける。`P` は目標と計算して一致すればよい

Base64 の 3 バイトの組の往復は、4 文字の読み取りを 1 つずつ書き換え、最後に帰納法の仮定で残りを書き換える 5 行の `%` の後に `{==}` を置いて通った。
`P` は目標の字面どおりでなくてよく、関数を 1 段展開した形で書いても通った。書き換えのあとでは場合分けできない（[language.md](language.md) の `match` の順の項）ので、
場合分けを先に別の def で済ませる。

### 入れ子の組から取り出した証明を 2 回使うには、複製する補題を通す

前提を `{a == True} & ({b == True} & {c == True})` で受け取ると、内側の要素には `+` を付けられない。
同じ証明を 2 つ渡す補題（`dup_t(p, G, +e, k)` が `k(e, e)` を返す形）を通して複製した。

### 中身をリストで持つ型は `--verdict` に拒まれる。中身も同じ型の構成子で表すと通る

JSON の配列を `JArr{xs: List<&2, J>}` と書き、`size(JArr{rest})` と組み直して自分を呼ぶと、`--check-only` は通るが `--verdict` は拒む
（下の「bend2 は通すがカーネルは拒む例」の bendlang/bend#1167 と同じ形）。配列の中身を同じ型の構成子 `JNil{}`・`JCons{head: J, tail: J}` で表すと通った。
代わりに `JArr{JNull{}}` のような形の崩れた値も作れてしまうので、「整形式」の判定 `wf` を書き、法則の前提に置いた。

### `--check-only` の出力の読み方

- 成功の `ALL PROOFS CHECK` は標準出力に、`SOME PROOFS FAIL` は標準エラーに出る
- 未完の法則（`N TODOs found`）が残っていても、ほかの def の誤りがあればそちらを先に出して落ちる。書きかけの途中でも、
  書いた分の補題が通っているかは、わざと壊して落ちるかで確かめられる
- 法則が計算で落ちたときの `expected` は `==` の左辺、`observed` は右辺の値だった

### 例の法則も、狙った壊し方で落ちるかまで確かめる

見出しの切り出しで「空行で見出しを終わらせない」壊し方をしても、最初に書いた例の法則は通った。例のメールでは、本文の `Subject:` が
「同じ項目の 2 回目」として捨てられ、壊れたことが結果に表れなかった。見出しに件名が無く本文にだけ `Subject:` があるメールを足すと止まった。
往復の法則も「仕様の符号化」と「実装の復号」が同じ向きに間違っていれば通るので、仕様の側を標準の例で押さえた。

## `--verdict` は型検査の二重目の網。カーネルは誤りを捕まえるが、網にも穴がある

`--verdict` は、bend2（TypeScript で書かれた型検査）が通した def を、Lean で証明された小さなカーネル（BendTT）でもう一度検査する。
`ALL PROOFS CHECK` になるのは、両方が受け入れ、`@unsafe` や外部のコードに頼っていないときだけ（`bend guide` の 328〜332 行）。
カーネルだけが捕まえる誤りは、bend2 が誤って通したものに限られる。macOS（bend 2.0.34、Lean 4.34.0）で 2026-10-01 に次を確かめた。

### カーネルは、bend2 を通さずに渡した偽の証明を拒む

`bend x.bend -o x.bendtt` でカーネルへの入力を書き出し、手で書き換えて、カーネル（`~/.bend/bendtt/<ハッシュ>/bendtt`）に直接渡した。

| 渡したもの | カーネルの判定 |
|---|---|
| `1 + 1 == 2` を `{==}` で証明（対照） | `ALL PROOFS CHECK`（終了コード 0） |
| 主張だけを `1 + 1 == 3` に書き換えた | `SOME PROOFS FAIL`、期待値と実際の値を示す（終了コード 1） |
| `1 + 1 == 3` を自分自身を呼ぶ def で「証明」 | `SOME PROOFS FAIL`、`calls that descend`（停止しない） |
| 同じ主張を、互いを呼び合う 2 つの def で「証明」 | `SOME PROOFS FAIL`、`calls that descend` |
| `Nat.add` の定義を「0 + y = y + 1」にすり替え、`1 + 1 == 3` を `{==}` で証明 | `ALL PROOFS CHECK` |

最後の行のとおり、カーネルが保証するのは「渡された定義のもとで証明が正しい」ことまでで、定義や法則が意図どおりに訳されたかは保証しない。
ガイドの「the translation has no proof, so read it to confirm a law」はこのことを言っている。

### bend2 は通すがカーネルは拒む例が、2.0.34 にもある

[bendlang/bend#1167](https://github.com/bendlang/bend/issues/1167)（未解決）の例は、2.0.34 でも `--check-only` が通り、`--verdict` が
「TypeScript の実装と形式化されたカーネルの食い違い」という知らせ付きで `SOME PROOFS FAIL` になった。構成子を組み直して自分を呼ぶ再帰
（`height(Node{rest})`）で、issue のコメントでは、bend2 が通す形は実際には必ず小さくなるので、偽を通したのではなくカーネルの規則が
狭いだけと分析されている。

偽を通した過去の例として、[bendlang/bend#902](https://github.com/bendlang/bend/issues/902)（2026-09-20 に修正済み）は、
`~` 引数を経由した 2 つの def の循環で `False{} == True{}` を `--check-only` に通していた。2.0.34 では bend2 の段階で
`a decreasing self-call` で止まり、カーネルまで届かない。issue の一覧で「verdict」を含むものは 46 件あり、うち 40 件が 2026-09-20 以降に立ち、21 件が未解決だった
（2026-10-01 に `gh search issues --repo bendlang/bend verdict` で数えた）。

### `--verdict` が、カーネルに見せないまま通してしまう def がある

[bendlang/bend#1186](https://github.com/bendlang/bend/issues/1186)（未解決）の穴も 2.0.34 で再現した。構成子の無い型の `~` 引数を
持つ def は、カーネルへの入力に載らず、範囲外とも報告されない。上の #1167 と同じ再帰をこの def の中に書くと、`--verdict` が
`ALL PROOFS CHECK` を出した。`~v: Void` を外しただけの同じ本体は、カーネルに渡って拒まれる。

```python
type Void is Data:

def skipped(~v: Void, t: Tree) -> Nat:   # Tree・Forest は #1167 と同じ
  match t:
    case Leaf{}: 0n
    case Node{End{}}: 1n
    case Node{Cons{+x, rest}}: Nat.max(1n+skipped(~v, x), skipped(~v, Node{rest}))
```

空の型の値は作れないので、この def は呼べず、ここから偽を導く方法は issue でも見つかっていない。法則の証明から呼ぶこともできなかった。
法則の `for` には `~` 引数を書けず（`expected : a name`）、証明の def から `helper(~v, n)` と呼ぶと、`~` には閉じた値しか渡せない
（`a template applied to closed ~ arguments`）と bend2 が止める。ただ「`--verdict` が通った def は
カーネルも検査した」とは言えなくなる。このリポジトリの証明は、`-o PROOF.bendtt` で書き出した入力に、法則 8 個（server 6 個、sort 2 個）が
すべて証明の本体付きで載っていて、`~` 引数を持つ def も無いので、この穴には当たっていない。

### 確かめ方に足すこと

上の「毎回ここまで確かめる」に加えて、`bend PROOF.bend -o PROOF.bendtt` を書き出し、法則の主張が訳されたあとも意図どおりであることを読む。
カーネルは定義のすり替えも、載らなかった def も教えてくれない。法則がすべて `LAWS.<名前> :` の形で載っていることは、commit 前のフックが
`.claude/hooks/laws-check.py` で機械的に確かめる（[claude-code.md](claude-code.md)）。手で照合したときは、名前空間の取り違えなどで
3 回数え直した。


法則の名前だけでなく、`PROOF.bend` から辿れる全ての def・法則・型が `.bendtt` に載っているかを見ると、#1186 で抜けた補助の def も捕まえられる
（[mcp-app.md](mcp-app.md) のサーバーではそうした）。法則から使われない def も `.bendtt` には載るので、「載っていない」は抜けの印になる。
名前は次の規則で付く。

- `PROOF.bend` 自身の def は、書いた名前のまま
- 取り込んだファイルの def は、`PROOF.bend` から見た相対パスから `.bend` を除き、英数字と `_` 以外を `_2f_`（`/`）・`_2d_`（`-`）のように 16 進で書いたものが接頭辞になる（`src/core/leaf-x.bend` の `one` は `src_2f_core_2f_leaf_2d_x.one`）。`import ... as M` の別名は効かない
- 法則を埋める def（`LAWS.<名前>`）は、別のファイル（`proofs/m.bend` で `import ../LAWS.bend as LAWS`）に書いても `LAWS.<名前>` のまま載る
- `~f: Nat -> Nat` のようなテンプレートの引数を持つ def は、使われた形ごとに `twice.qv` のような名前で載る

## このサーバーで証明したこと、しなかったこと

証明した法則は 6 つ。どれもサーバーの純粋な部分についての主張で、`bend PROOF.bend --verdict` も通っている（クラウド環境で確認）。

| 法則 | 内容 |
|---|---|
| `root_page` | `/` への応答は決まった挨拶 |
| `hello_echo` | `/hello/<name>` の応答は、name をそのまま埋め込んだ 200 |
| `utf8_bytes` | `utf8.bytes` は、仕様どおりに符号化したバイト列の長さに等しい |
| `response_format` | 応答の形式全体（Content-Length が本文のバイト数で、空行の後に本文が続く） |
| `path_of_request` | 空白を含まない method と path なら、`path_of` は path を取り出す |
| `hello_request` | `<method> /hello/<name> <rest>` を受けると、name 入りの 200 を返す（`path_of` と `route` をつないだ全体） |

証明の範囲外として残したもの:

- `handle` などの入出力の部分。法則が述べているのは `route(path_of(req))` という純粋な部分だけで、
  接続の処理が実際にこの組み合わせを呼んでいることは述べていない。
- リクエスト行が分割されて届く場合。`TCP.recv` は 1 回（4096 バイト）しか読まない。
- `/pow2` と 404 のルーティング。
- メソッドの区別。GET 以外にも同じ応答を返す。
- パスのパーセントエンコードの復元（[language.md](language.md)）。
- 起動の部分（`main` と、待ち受け先 `BEND_HOST` の読み取り）。

公式のデモ（`io_http_server`）が証明しているのも、純粋な関数 `http_response` だけ
（「空行の後に本文」「応答が同じなら元のページも同じ」）だった。

## 並列ソートで証明したこと

`sort/` は、parallel let で左右を並列に整列する並列マージソートと、その正しさの証明である。公式の demo のうち、並列の bitonic sort
（`pure_par_sort`）が証明しているのは「葉の総和が変わらない」ことだけで、整列と並べ替えを証明している `proof_insertion_sort` は
逐次の挿入ソートだった。`sort/` はその間を埋める。

| 法則 | 内容 |
|---|---|
| `sort_sorted` | `sort` の出力は昇順に並んでいる |
| `sort_perm` | どの値 x も、`sort` の出力の中に、入力の木の葉と同じ回数だけ現れる（並べ替えである） |

`bend PROOF.bend --check-only` と `--verdict` の両方が ALL PROOFS CHECK（`--verdict` は Windows の Lean 入りのイメージで確認）。
今の版は、比較に Base の `Nat.is_le`（Bool を返す）を使い、補題は 11 個、PROOF.bend は 179 行。鍵の補題は
「`Nat.is_le(x, y)` が True なら x ≤ y、False なら y ≤ x」（`is_le_ev`）で、`Nat.cmp` と同じく 2 つを同時に減らす帰納法で示した。

最初の版は、比較に `proof_insertion_sort` の `le_case`（どちらが小さいかの証拠を返す比較）を出典を書いて借り、補題 9 個・146 行だった。
これが遅かったので、法則（`LAWS.bend`）は変えずに、実装を `Nat.is_le` に替えて証明を書き直した（下の「速さ」）。
法則を固定したまま実装を差し替え、証明だけを直して済んだのは、法則駆動の開発の使い方そのものである。

実装を壊した写しで検査すると、壊した場所に応じた法則で落ちた。merge の代わりに単につなぐと `sort_sorted` で、葉を 2 回出すと
`sort_perm` で落ちた。

### 比較の結果で分けるときは、枝を関数で渡す

`match` は計算した値を受けない（`a match cannot scrutinize a computed value: give it its own def`）。そこで比較の結果（今の版は Bool、
最初の版は証拠）を引数に取る `branch(c, u => …, u => …)` を作って分けた。枝を値で渡すと両方とも計算されるので、`u => …` の関数で渡す。
再帰呼び出しがこの関数の中にあっても、停止性の検査は通った。

### 組み直した引数も「変わらない引数」として扱われる

Base の `List.merge` は停止のために燃料を持つが、`sort/` の `merge` には要らなかった。`merge(x <> xt, yt)` のように、
`match` でばらした第 1 引数を組み直して渡しても、停止性の検査は「変わらない引数」として受け、第 2 引数が小さくなることで通った。

### 証拠の値も 1 回しか使えない

`Sorted.from` は Type を返すので、その証拠は affine で、2 本の帰納法の仮定の両方に渡すことはできない。部分の証拠は補題（`.fin`）に
渡し、分岐ごとに 1 回ずつ使う形にした。

### 速さ: 比較を `Nat.is_le` に替えると、2^17 個が 30 秒から 65 ms になった

最初の版は遅く、入力が倍になると約 4 倍かかった。比較を Base の `Nat.is_le` に替えた今の版は、次のとおり（Windows の wslc、
ネイティブビルド、`--gpu off`。`bench/run.sh sort` で測った。時間は入力の生成と結果の検査を含む実時間。生の値は
`bench/results/ryzen5-3600-wslc/sort.tsv`）。

| 入力の個数 | 1 スレッド | 12 スレッド | 最初の版（1 スレッド） | 最初の版（12 スレッド） |
|---|---|---|---|---|
| 2^15 | 19・23 ms | 15・19 ms | 1,751・1,914 ms | 670・728 ms |
| 2^16 | 35・38 ms | 18・19 ms | 7,235・7,183 ms | 2,520・2,567 ms |
| 2^17 | 63・65 ms | 29・31 ms | 30,067・30,056 ms | 10,795・10,660 ms |
| 2^20 | 471 ms | 187 ms | （測らず） | （測らず） |

入力が倍になると時間もほぼ倍になり、n log n の形に戻った。12 スレッドの伸びは 2 倍ほどで、最上段の merge が逐次に全体をなめる分が
効いていると考える。

#### 原因は `le_case` だった。枝を関数で渡す形と、引数の `+` は関係なかった

最初の版の merge を少しずつ変えた写しで、2^16 個の整列を測って切り分けた（12 スレッド、各 1 回）。

| merge の書き方 | 2^16 個 |
|---|---|
| 最初の版（`le_case` の証拠を `branch` に渡し、枝は関数） | 2,881 ms |
| 比較だけ `Nat.is_le` の Bool に替えた（枝は関数のまま） | 19 ms |
| `le_case` のまま、結果を Bool に直してから枝分け | 3,263 ms |
| `Nat.is_le` で比べ、段階の引数で比べる段と出す段を 1 つの def にまとめた（関数も `+` も使わない） | 10 ms |
| 上の版の引数にだけ `+` を戻した | 14 ms |

`le_case` は、2 つの Nat を 1 ずつ減らしながら比べる、自分で書いた再帰である。値の大きさに比例する手間がかかり、整列する値は最大で
入力の個数まであるので、全体が 2 乗に近くなったと推定している。Base の `Nat.is_le`（中身は `Nat.cmp` で、同じく 1 ずつ減らす再帰として
書かれている）は速いので、コンパイラが Base の比較を特別扱いしているとみているが、生成された C では確かめていない（未確認）。

ただし、`le_case` を 1 回だけ呼ぶ別のプログラムでは、40 億どうしの比較が数 ms で終わった。この食い違いは説明できていない。
AI に書かせた実験でも、値が等しいかを自前の再帰で判定した実装だけが遅かった（[ai-proofs.md](ai-proofs.md) の連長圧縮）。
比較は Base の関数を使い、証明の側で「Base の比較の結果が何を意味するか」を補題で示すのが安全と考える。

最初の版について、macOS（Apple M2）でも測った（生の値は `bench/results/m2-macos/sort.tsv`）。

| 入力の個数 | 1 スレッド | 8 スレッド |
|---|---|---|
| 2^15 | 907・296 ms | 130・133 ms |
| 2^16 | 1,574・1,202 ms | 420・433 ms |
| 2^17 | 5,429・5,063 ms | 1,724・1,727 ms |

M2 でも、入力が倍になると約 4 倍かかった。1 スレッドの時間が Ryzen の記録の約 6 分の 1 で、mandelbrot の 1 スレッドでは両機がほぼ同じ速さ
だったこと（[benchmarks.md](benchmarks.md)）と合わないが、追っていない。
