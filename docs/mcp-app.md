# 証明付きで実用の道具を書く: メールボックスを読む MCP サーバー

この検証のあと、Bend 2（v2.0.34）で実際に使う道具を 1 つ書いた。Thunderbird のローカルの受信箱（mbox）を読み、新しいメールの件名・差出人・日時・Message-ID を返す MCP サーバー（標準入出力で JSON-RPC を話す）である。Claude Code から呼ぶことを想定している。書いたのはほぼ全部 Claude（Opus）で、人は法則の案を承認し、設計の分かれ目を選んだ。

この文書は、その記録から Bend 2 に関わる部分を抜き出したもの。書き方の落とし穴は [language.md](language.md)、証明のこつは [proofs.md](proofs.md) に足した。リポジトリは公開していないので、必要なコードはここに載せる。

## 結論: 書ける。証明は核の正しさを守り、外の実装との突き合わせが残りを守る

- 223 MB の受信箱から 500 件を 7 秒前後、最大メモリ 9 MB で返す（ネイティブ版、Apple M2）。目標の 10 秒に収まった。
- 法則は 31 個。UTF-8 の復号、JSON の生成と解析、MCP の応答、mbox の区切り、見出しの符号化語（RFC 2047）の復号について、往復・1 行に収まること・区切って読んでも同じこと・境目の例を証明し、`--verdict`（Lean のカーネル）も通した。
- 実際に見つかった不具合は、証明ではなく外の実装との突き合わせが捕まえた。JSON の解析器が `-` だけを数として受け付けていたのは Python の `json` と、UTF-8 の復号器の置き換えの単位の誤りは処理系の復号と比べて見つかった。証明は書いた法則の範囲しか守らない。
- 入出力（ファイルの読み込み、標準入出力のループ）は証明の外に置き、ネイティブ版を動かす試験で確かめた。

## 作ったもの

| 部品 | 中身 | 法則 |
|---|---|---|
| UTF-8 の復号器 | バイト列を文字列にする。不正な並びは Unicode 標準の maximal subpart ごとに U+FFFD | 出力は全部スカラー値、往復で戻る、ASCII はそのまま、置き換えの例 |
| JSON | 生成と解析。数は字句のまま持つ | 往復で戻る、生成した文字列に改行が無い、解析の結果は整形式、例 |
| MCP | 行の分割、要求の振り分け、応答の組み立て | 区切って渡しても同じ、id を持つ要求には同じ id で答える、通知には答えない、どんな入力にも 1 行で答える、例 |
| mbox | 区切り行の判定、見出しの切り出し | 区切って渡しても同じ、読み込みのループの模型が一度に読むのと同じ、例 |
| 符号化語 | `=?UTF-8?B?...?=` の復号。文字の途中で切れた語もつなげてから復号する | Base64・Q の往復、つなげて復号しても 1 つずつ復号しても同じ、例 |

置き場は、核の実装（`src/`）、法則だけを並べた `LAWS.bend`、法則が使う仕様の関数（`specs/`）、証明（`proofs/`）、それらを取り込むだけの `PROOF.bend`、入出力の殻（`app/`）に分けた。法則は人が読んで承認するので、`LAWS.bend` を開けば何を保証しているかが一覧できるようにした。法則ごとに「主張・なぜ・確かめ方」を日本語で書いた一覧も置き、法則の名前と一覧の見出しが 1 対 1 で対応しているかを試験で確かめた。

## 証明を通すために設計を変えたこと

最初に素直に書いた形の多くは、証明の途中で計算が止まった。通る形に寄せた設計の指針は次のとおり（詳しくは [proofs.md](proofs.md) の「実用の道具で証明したときのこつ」）。

- ビット演算ではなく、`U32{WCon{b0, WCon{b1, ...}}}` でビットを直接組み立てる。UTF-8 の往復は、これで計算だけで閉じた
- 「スカラー値である」のような不変条件は、値を作る唯一の関数で検査し、作った値に証明を持たせる（依存ペア）。性質は中身を追わずに型から言える
- 1 バイトずつ進む状態機械にする。「区切って何回に分けて渡しても同じ」が帰納法の 3 行で出る
- 64 通りのような場合分けの木は Python で生成し、生成したものと証明のファイルが一致するかを試験で確かめる
- 中身をリストで持つ型（`JArr{xs: List<J>}`）は `--verdict` に拒まれた（bendlang/bend#1167）。中身も同じ型の構成子で表した

## 証明と試験は、捕まえるものが違った

法則を足すたびに、実装か法則を 1 か所だけわざと壊し、狙った法則で落ちるかを確かめた（25 通り）。そこから分かったこと:

- 一般の法則が言わない振る舞いは、証明では捕まらない。UTF-8 の復号器で `ED` の後の範囲を広げても、「出力は全部スカラー値」「往復で戻る」は成り立ったまま通った。違うのは U+FFFD の個数で、処理系の復号との突き合わせが捕まえた。そのあと、範囲の境目の例を法則に足した
- 例の法則も、書いただけでは何も守っていないことがある。見出しの切り出しで「空行で見出しを終わらせない」壊し方は、最初の例では結果に表れず通った。例を書いたら、狙った壊し方で実際に落ちるかまで確かめる
- 往復の法則は「仕様の符号化」と「実装の復号」が逆どうしであることしか言わない。両方が同じ向きに間違っていても通るので、仕様の側を標準の例（RFC 4648 の Base64 の例など）で押さえた
- ビットを組み立てた仕様の関数は人が読んでも正しいか判断しにくい。同じ仕様を Python で素直に書いた読める版を置き、全域（UTF-8 は U+0000〜U+10FFFF の全部）で突き合わせた

外の実装との突き合わせは、Python の `json`、処理系の UTF-8 の復号（`File.read` の `io_str`）、Python の正規表現で書いた読める版、既存の Python の道具と行った。実際の受信箱でも、手元の 7 つの受信箱で、メールの数が既存の Python の道具と一致し、見出しの食い違いはすべて理由が分かる（UTF-8 以外の文字コードをそのまま返すなど）ことを確かめた。

## 速さ: 時間のほとんどは 1 バイトずつの状態機械

| 段 | 時間（223 MB） |
|---|---|
| `File.read_at` で 64 KiB ずつ読むだけ | 0.6 秒 |
| ＋区切り行の判定（状態機械） | 4.3 秒 |
| ＋見出しの切り出し | 7.1 秒 |
| ＋符号化語の復号と JSON（500 件） | 差はばらつきに埋もれた |

Apple M2、macOS、ネイティブ版、2026-10-02、各 3 回。読み取りのバイト列は `List<U32>` の連結リストで返り、1 バイトごとに状態のレコードを組み直すので、読み取りだけの 7〜10 倍かかる。メモリは 64 KiB の区切りで数 MB に収まった。`bend x.bend`（JS で実行していると推定）では同じ読み取りに約 280 MB 使ったので、常駐させるサーバーはネイティブ版にする。

## 証明の外に残ったもの

- 入出力の殻。ファイルを区切って読むループは、同じ形のループを「位置と長さを渡すとバイト列を返す関数」で回す模型として証明したが、実際のループと模型が同じ形であることは機械では確かめていない。区切りの大きさを 1〜65536 バイトと変えて結果が同じかを見る試験で埋めた
- `--verdict` の穴（bendlang/bend#1186）。法則の名前だけでなく、`PROOF.bend` から辿れる全ての def・法則・型がカーネルへの入力に載っているかを、書き出した `.bendtt` を読むスクリプトで毎回確かめた（名前の規則は [proofs.md](proofs.md)）
- 速さ。法則は速さを縛らない（[ai-proofs.md](ai-proofs.md) と同じ）

## 書いてみた感触

型検査のエラーの文面から原因を引けるようになるまでが重かった。`a filled definition (an unfilled law is a dead claim ...)` が「下に書いた def を呼んだ」か「相互再帰」を意味する、のように、文面と原因の対応は [language.md](language.md) の各項に書いた。対応が分かってからは、法則を先に決めて実装と証明を書く流れは安定し、証明が通った部品は、組み合わせたあとに壊れることがほとんどなかった。

一方で、証明の行数は実装より多くなった（JSON は実装 885 行に対し証明 1,781 行で、一部は生成した場合分けの木）。法則を足すたびに「わざと壊す」「外の実装と突き合わせる」「カーネルへの入力を確かめる」の 3 つを回したので、1 つの部品にかかる手間は大きい。ふつうの言語で試験だけを書く場合と比べて測ってはいない。
